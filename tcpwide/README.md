# tcpwide

面向**多地区、多设备**客户端的一套 TCP 配置。一个脚本，直接落地，可完整还原。

```bash
curl -fsSL https://raw.githubusercontent.com/bear4f/routetune/main/tcpwide/tcpwide.sh -o /tmp/tcpwide.sh

sudo bash /tmp/tcpwide.sh install    # 向导：问出口带宽、覆盖 RTT、档位，装好软链
sudo tcpwide                          # 之后直接进面板
```

## 面板

```
  出口带宽   500 Mbps（整形到 95% = 475 Mbps）
  覆盖 RTT   250 ms  ← 按最远的客户端，不是按你自己
  拥塞控制   bbr（主线只有 v1，容量剧变后估值滞后）
  根队列     mq 0: root
  缓冲上限   29.8 MB/socket ｜ 全局 tcp_mem 高水位 328.4 MB（约 11 条满上限就触发压力）
  首窗       initcwnd 10（内核默认 10）
  持久化     否（重启后失效）
  [!] 实际生效的队列是 mq，与配置不一致
      可能是重启后没应用，或被别的服务覆盖。按 a 重新应用
──────────────────────────────────────────────────────────────────────
  档位                                          ▸ 当前
    1) 稳定优先   整形 90%｜首窗 16  丢包敏感、跨境线路
  ▸ 2) 均衡       整形 95%｜首窗 20  推荐
    3) 速度优先   整形 98%｜首窗 32  干净直连
    4) 不整形     只做 pacing  放弃按设备公平和 AQM
  设置
    5) 出口带宽    6) 覆盖 RTT    7) 首窗
  查看与工具
    8) 状态与诊断（实时重传率、队列、冲突）
    9) 预演（逐项列出 当前值 → 目标值 和理由）
    a) 重新应用     p) 持久化开关     r) 完整还原     0) 退出
```

**档位只改三个数**（整形百分比、首窗、要不要整形），不引入新机制——预设如果偷偷换掉
底层机制，面板显示的就不是实际在跑的东西了。

面板顶部两个动态项值得注意：

- **队列漂移**：配置说 cake、实际是 `mq`/`htb` 时直接报警。重启后没应用、或被别的
  服务覆盖，都会在这里现形
- **全局 `tcp_mem`**：`rmem_max` 是**每 socket** 的上限，`tcp_mem` 是**全机所有 TCP 共享**
  的页预算。只显示前者是漏了一半——小内存机器上几条满上限的连接就会先撞全局压力，
  内核开始缩所有 socket 的缓冲

`8) 状态与诊断` 里的重传率是 **5 秒窗口的增量**，不是自开机累计。跑了几周的机器上，
累计值是个动不了的平均数，看不出你刚才那次改动有没有用。

命令行仍然可用（`check` / `plan` / `apply` / `status` / `revert` / `uninstall`），
非 TTY 下自动退回命令行模式，脚本化调用不受影响。

## 核心判断：分散的客户端不需要「每人一套参数」

per-route 能写的参数（`initcwnd` / `initrwnd` / `rto_min` / `advmss` / `congctl`）
几乎全是**新连接头几个 RTT** 的事。看片是长连接，这些参数对播放中途的丢包和尾峰
毫无作用。给每个地区单独配一套参数，听起来对，实际能配的东西是空的。

真正有用的是**一套按最远客户端定尺寸的配置**，加上会自己适应其余客户端的机制：

| 机制 | 解决什么 |
|---|---|
| **pacing** | 突发不会按线速灌进最慢那条末端链路 —— 混合客户端下降低重传的最大单一杠杆 |
| **BBR** | 不把随机无线丢包当拥塞信号。丢包型算法每丢一次砍一次窗，5G 上永远起不来 |
| **AQM + ECN** | 真排起队时是标记而不是尾部丢包 |
| **按设备公平** | 一台开 40 条连接的设备挤不掉只开 1 条的那台 |

**刻意不做的事：不设单流限速。** 按固定宽带调的限速会勒死固定宽带，而对移动客户端
根本不会触发 —— 它本来也没跑那么快。

## 三个目标各自靠什么

### 低重传

`fq`/CAKE 的 pacing 是第一位的。没有 pacing 时，一个 cwnd 的数据会按网卡线速打出去，
末端是 5G 或家宽时缓冲直接被冲垮。

第二位是**把瓶颈拿回本机**。VPS 出口通常被运营商限速，队列堆在他们那边——而运营商的
policer 是**丢包**式的。整形到限速的 95%，瓶颈回到本机，换成 CAKE 的**排队 + ECN 标记**。
让出 5% 峰值换真实的重传下降。

### 爬升快

- 缓冲上限按 **覆盖 RTT × 出口带宽** 的 BDP 两倍算，别让远端客户端撞到硬顶
- 默认路由 `initcwnd 20`（内核默认 10）。前面有 pacing，这一发会被摊到一个 RTT 上
- **`tcp_no_metrics_save=1`** —— 内核默认会把每个目标的 `ssthresh` 缓存下来。5G 波动时
  缓存到一个很低的值，**下一条连接会带着这个悲观值起步、提前退出慢启动**。这是波动
  链路「爬不起来」的一个直接原因，默认没人关
- `tcp_slow_start_after_idle=0`

### 稳定不掉速

- BBR 不因随机丢包塌陷
- 不设会绑死的单流限速
- `slow_start_after_idle=0`：流媒体分块之间的短暂空闲，默认行为是把 cwnd 打回初始值
  重新慢启动 —— 这是「看着看着掉速」的一个真实机制
- **按设备公平**：`fq` 是按**流**公平的。一台设备 38 条连接、另一台 1 条，`fq` 下带宽是
  38:1。CAKE 的 `dual-dsthost` 先按主机公平、再在主机内部按流公平，变成 50:50

## 为什么整形是可选但推荐的

主机公平和 AQM **只有在瓶颈队列在本机时才存在**。不整形就拿不到，只剩 pacing + BBR +
缓冲尺寸。`--no-shape` 保留这个选择，但那时脚本不会声称自己做到了公平。

## 覆盖 RTT 怎么填

**填「这台机器上最远那个客户端」的延迟。** 不是你自己到这台机器的延迟，也不是平均值。

上限只是上限：近端客户端的 autotuning 会自己停在低处，用不到那么多。但填低了，
**每个远端客户端都会撞到一个查不出原因的硬顶**。

向导和面板的 `6)` 都会**直接量一次**当前活跃客户端，给出建议：

```
  实测：当前 2 个活跃客户端里，最远的 RTT 是 277 ms
  建议填 350（实测 ×1.2 后向上取整，给移动客户端留波动余量）
```

量的时候只算**入站且真的在传数据**的连接——本机往 CDN/源站开的出站连接不是客户端，
空闲 socket 上那个 `rtt` 是陈旧值不是路径采样。

**填大不是没有代价**，向导会把这个权衡摆出来（958 MB 内存 / 500 Mbps 为例）：

```
    100 ms → 上限 11.9 MB/socket，约 27 条满上限就触发全局 tcp_mem 压力
    250 ms → 上限 29.8 MB/socket，约 11 条满上限就触发全局 tcp_mem 压力
    400 ms → 上限 47.7 MB/socket，约  6 条满上限就触发全局 tcp_mem 压力
```

所以**每台机器分别填**：同区域落地（客户端 30-60 ms）填 100 上下，跨洋中转
（客户端 150-280 ms）填 250-350。同一套配置抄到所有机器上，要么把近端机器的
内存预算白占掉，要么把远端机器的客户端封顶。

## 尺寸怎么定

覆盖 RTT 默认 **250 ms**，按**你最远的客户端**填，不是按你自己。

这条来自 [tcpfit](https://github.com/Kylin010/tcpfit)：它把 RTT 探测整个删掉改成硬编码，
理由是代价不对称 —— 估高只多付一点拥塞控制超发，**估低是每个远端客户端都撞得到、却
查不出原因的硬顶**。

缓冲上限 = BDP × 2（`tcp_adv_win_scale=1` 时内核只把一半交给应用），下限 8 MiB，
再按内存 1/16 夹住（上限是**每 socket** 的，不夹住就是小机器被自己的配置 OOM）。

## 每个键只往安全的方向动

| 方向 | 键 | 规则 |
|---|---|---|
| 只升不降 | `rmem_max` `wmem_max` `tcp_rmem` `tcp_wmem` | 上限给大几乎不亏（autotuning 会自己停在低处），调小是查不出来的硬顶 |
| 只降不升 | `tcp_notsent_lowat` | 运维已经调得更紧就保持 |
| 精确 | 其余 | 就是要这个值 |

`tcp_rmem` / `tcp_wmem` 是 `min default max` 三元组，**逐字段合并** —— 不会在同一次写入
里升一个、缩另一个。

## 安全边界

- `plan` 只读；`apply` 写之前先快照 sysctl、根队列、默认路由
- `revert` 还原到 tcpwide 介入之前，并清除持久化
- **默认路由是 ECMP、多路径、或不止一条时，一律不动** —— 错改默认路由的代价是断连
- 检测到 netshape / routetune 会中止（两者同样接管全局 sysctl 和根队列，不是叠加，
  是谁后跑谁生效）。**tcpwide 不替你卸载它** —— 卸载得由它自己的代码做，它知道自己
  改过什么（HTB 类、nginx 片段、systemd unit、自己的 sysctl 快照），tcpwide 猜不到。
  确认要覆盖才加 `--yes`
- 默认**不持久化**，重启回到原样；`--persist` 才写 `/etc/sysctl.d` 和 systemd unit

## 从 tcpfit 和 netshape 借的（v0.3.0）

**`tcp_mem`（来自 tcpfit）** —— `rmem_max` 只是天花板，`tcp_mem` 才是内核硬拦的**全局**
页预算。它太小的话，上限调多大都没用：几条大流一上来就触发压力，内核把所有 socket 的
缓冲统统缩回去。按 tcpfit 的公式取内存的 1/16、1/8、1/4。

**每 socket 上限改夹在 RAM/32（来自 tcpfit）** —— 原来夹 RAM/16。tcpfit 的推理更好：
单个 socket 最多占全局预算的 1/8，也就是**至少保证 8 条大流能同时到顶**。而预算本身是
内存的 1/4，所以夹子落在 RAM/32。

**`+2 MiB` 固定余量（tcpfit 实测）** —— 纯 2×BDP 没有余量。tcpfit 在 300M/168ms 真机上
A/B 过：11.25 MB 平均收 257.3 Mbps，同样的缓冲 **加 2 MiB 后 272.7 Mbps**，两边都是零重传。

**`tcp_adv_win_scale=1` 和 `tcp_moderate_rcvbuf=1` 显式写死** —— 上面所有上限都是按
「应用拿到一半」算的。内核要是设成 2，应用只拿到四分之一，**那些数全部差一倍**。而关掉
autotuning 的话上限就是摆设，连接永远停在默认值涨不上去。假设必须写出来，不能默认。

**`tcp_ecn=0`（来自 netshape）** —— 我原来设 2，理由是「被动模式不主动要求，所以安全」。
netshape 明确关掉它，理由是**跨境中间盒会 blackhole ECN 协商**。那是实战结论，比我那条
理论强，而且这里恰好全是跨境路径。关掉后 CAKE 改用丢包发信号，仍然比运营商 policer 温和。

**`tcp_notsent_lowat` 默认 131072（真机夹逼对照）** —— netshape 的逻辑是 RTT ≥120ms 就设
16384，对 seek 延迟合理，对吞吐是反的：**400 Mbps 下 16 KB 只够发 0.33 ms**，代理进程
必须在这个时间内跑完一整轮「唤醒 → 读上游 → 解密 → 写下发」。

真机实测见下。它仍然是面板里的 `n)`，填 0 保持系统现值。

## 怎么在会漂移的路径上做对照

跨境路径在晚高峰的波动比你能调出来的任何差异都大。所以**单次 A 对单次 B 没有意义**，
必须用 **A → B → A 夹逼**：

```
22:26:33  16384    均 271.30  峰 421.50
22:40:05  131072   均 257.36  峰 330.02
22:41:05  16384    均 213.31  峰 288.99
```

两次 16384 之间路径自己劣化了 **-21%（均）/ -31%（峰）**。直接看原始数字，131072 的 257
夹在 271 和 213 中间，会得出"没差别"。用两次 16384 插值出 22:40 那一刻的基线再比：

```
16384（插值）   均 217.3   峰 298.1
131072（实测）  均 257.4   峰 330.0     →  +18.4%  /  +10.7%
```

**方向和机制预测的一致。** 但只有一个 B 样本、趋势只由两点估出，证据不算强 —— 要坐实
就再多跑几组 A/B/A/B/A。

更省事的办法是 `8) 状态与诊断` 里的**窗口内最高单流速率**：它在已经跑着的真实流量上
连续采样，想采多久就采多久，直到把噪声投票投掉。跑分那 9 秒受路径当时的拥塞支配。

客户端分布用 `routetune scan`——那是另一个工具的活。

## 整形的代价，说在前面

**单线程测速正是这套设计主动交换掉的那一面。** 整形按定义让出 5% 峰值，而按设备公平对
单线程跑分毫无帮助——它换来的是多设备并发时不会被一台设备挤掉。

而且 CAKE 不是免费的：它把整个出口收敛到一个 qdisc 并逐包处理。**单核 VPS 跑几百 Mbps
时，这笔 CPU 开销可能比它替掉的 policer 还贵。** `check` 和面板会在核数不够时直接警告，
单线程掉速就先用「4) 不整形」档对照一次。

## 做不到的事

无线层丢包服务端消不掉。BBRv3 从来没进过主线，要换内核（XanMod），脚本给不了 ——
`check` 会告诉你当前内核实际能提供什么。
