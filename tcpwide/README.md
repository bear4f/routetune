# tcpwide

面向**多地区、多设备**客户端的一套 TCP 配置。一个脚本，直接落地，可完整还原。

单线程实测（BandwagonHost 洛杉矶 → 上海电信，133ms）：**平均 1.08 Gbps / 峰值 1.40 Gbps**。

## 安装

```bash
curl -fsSL https://raw.githubusercontent.com/bear4f/routetune/main/tcpwide/tcpwide.sh -o /tmp/tcpwide.sh
sudo bash /tmp/tcpwide.sh install
```

向导会问端口速率、覆盖 RTT 和档位，不预先写死参数。**已经装过也跑同一条命令升级。**

想钉死版本就把 `main` 换成 tag，例如 `v1.0.0`。

装完直接进面板：

```bash
sudo tcpwide
```

不进向导、直接给参数：

```bash
curl -fsSL https://raw.githubusercontent.com/bear4f/routetune/main/tcpwide/tcpwide.sh \
  | sudo bash -s -- install --egress 2000 --profile noshape
```

> **不要用 `sudo bash <(curl …)`。** `sudo` 默认关掉 2 号以上的文件描述符，
> 而 `<(…)` 造出来的 `/dev/fd/63` 属于外层 shell，`sudo bash` 启动时它已经没了。
> 已经是 root 时去掉 `sudo` 才能用。
>
> **`curl … | bash` 时 stdin 就是脚本本身**，向导提问会把脚本下一行当成你的回答读走。
> 所以管道那条必须用 `--egress` 把参数给全。

## 选哪个档位

| 档位 | 什么时候用 |
|---|---|
| **4 不整形** | **默认推荐。** 只做 pacing，不接管整形。CPU 不够时这是最快的 |
| 3 整形 98% | 几乎等于不整形，但付全额 CAKE 开销 |
| 2 整形 95% | 多设备共享，要按设备公平 |
| 1 整形 90% | 丢包敏感、跨境线路，要 AQM |

整形（CAKE）能给你**按设备公平**和 **AQM**，代价是每包 CPU 开销。
小机器上这笔开销可能比它替掉的运营商 policer 还贵——实测同机同后端，
不整形峰值 629 Mbps，整形只有 332。所以 `check` 会在核数撑不住端口时提醒你。

**覆盖 RTT 填最远那个客户端的延迟，不是你自己的。** 缓冲按它定尺寸；
填小了就是每个远端客户端都撞得到、却查不出原因的硬顶。

## 安全边界

- **首次 apply 前自动快照** sysctl、根队列、默认路由，`revert` 完整还原到介入之前
- **apply 完自动回读验证**，不一致就把「目标 vs 实际」逐行打出来
- **每个键只往安全的方向动**：上限类只升不降，行为类精确设置
- 检测到 `netshape` / `routetune` 会**中止**——同一台机器只能留一个接管根队列的工具
- 默认写 `/etc/sysctl.d/90-tcpwide.conf` 和一个 systemd unit，重启后仍在

```bash
sudo tcpwide status      # 当前状态和指纹
sudo tcpwide plan        # 预演：逐项列出 当前值 → 目标值 和理由，什么都不写
sudo tcpwide revert      # 完整还原
sudo tcpwide uninstall   # 还原并卸载
```

## 排查掉速用 `8`

**在测速跑到一半的时候按 `8`。** 空闲机器上那些数字什么都不说明。

一个 8 秒窗口内同时采：重传增量、每核占用、每秒 `ss` 快照、队列统计、网卡计数。
然后逐条连接给出**证据**，不是猜测：

```
[入站：对方连进来]  窗口内实测 426.1 Mbps
[::ffff:58.38.51.162]:5602  RTT 131.8 ms
  在途        22.5 MB（unacked 16308 × mss 1448）
  拥塞窗口    64.8 MB（cwnd 46935 × mss）
  对端窗口    22.5 MB（snd_wnd）＝ 131.8 ms 上 1432 Mbps 的上限
  每秒        1400 1400 120 100 1400 1400 110 90 Mbps
  抖动        最低 90 / 中位 760 / 最高 1400 Mbps
  → 指向对端接收窗口：在途已是 snd_wnd 的 100%，压在它上面。
    本机怎么调都拿不回来——那是客户端的 rmem。
```

四种天花板各由**一个字段**判定，一个都不靠推测：

| 现象 | 指向 |
|---|---|
| `rwnd_limited` 高，或在途 ≈ `snd_wnd` | 对端接收窗口（本机改不了） |
| 在途 ≈ `cwnd × mss` 而 `rwnd_limited` ≈ 0 | 拥塞窗口 / 路径丢包 |
| 实测 ≈ `pacing_rate`，队列 `overlimits` 非零 | 本机 pacing / qdisc |
| 最忙单核接近 100% 而平均低 | 用户态代理 / 加密 |

中继有两段 TCP，按监听端口分开列，还会**按秒对齐**——
下游掉的那几秒上游也在掉，就是上游供给不足，发送侧旋钮改不动它。

按 `8` 时会**自动记一行**到跨地区表（地区按对端 IP 自动识别，不用填）。
`t` 按「配置 × 地区」聚合，给出**跨地区中位**和**最差地区**：

```
  地区（对端地址）          样本    中位    最差    抖动      RTT
  58.38.51.162                 2     202     190   3.1×   141 ms
  183.63.1.10                  1     122     122   4.8×   169 ms
  ────────────────────────────────────────────────────────────
  跨地区中位 202   最差地区 122   平均抖动 3.0×
```

**一套配置只有这两个数同时变好才算赢。** 一个地区冲到 1.5 Gbps 而另一个躺在 120，
不是改进。

## 它改变不了的

- **不同地区之间的差距。** 同一台机器、同一分钟、RTT 几乎一样的四个后端，
  平均速度可以差 6 倍。那是回程路由和后端，服务端 sysctl 碰不到
- **对端的接收窗口。** 实测抓到过在途 = `snd_wnd` 的 100%
- **无线末端的丢包。** BBR 不把它当拥塞信号，但消不掉它
- **单核 CPU 上限。** 用户态代理和加密基本只用得到一个核
