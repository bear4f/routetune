# tcpwide

面向**多地区、多设备**客户端的一套 TCP 配置。一个脚本，直接落地，可完整还原。

**一键安装（进向导）**

```bash
curl -fsSL https://raw.githubusercontent.com/bear4f/routetune/main/tcpwide/tcpwide.sh -o /tmp/tcpwide.sh && sudo bash /tmp/tcpwide.sh install
```

**一键安装（不进向导，直接给参数）**

```bash
curl -fsSL https://raw.githubusercontent.com/bear4f/routetune/main/tcpwide/tcpwide.sh \
  | sudo bash -s -- install --egress 500 --profile noshape
```

装完直接进面板：

```bash
sudo tcpwide
```

> **不要用 `sudo bash <(curl …)`。** `sudo` 默认关掉 2 号以上的文件描述符，而 `<(…)`
> 造出来的 `/dev/fd/63` 属于外层 shell——`sudo bash` 启动时它已经没了，报
> `/dev/fd/63: No such file or directory`。已经是 root 时去掉 `sudo` 才能用。
>
> **`curl … | bash` 时 stdin 就是脚本本身**，向导提问会把脚本下一行当成你的回答读走。
> 所以管道那条必须用 `--egress` 把参数给全，缺了会直接报错并告诉你该用哪条。
>
> 脚本本身也做了对应处理：从管道运行时 `BASH_SOURCE` 要么为空、要么指向一个 bash 还在读的
> `/dev/fd` 管道（直接复制会装进截断的文件），这两种情况都会重新抓一份完整的，
> 并检查抓到的确实是本脚本再落盘。

`--profile` 可选 `stable | balanced | speed | noshape`，`--buf-mb N` 指定缓冲上限（0=自动），
其余参数见 `--help`。

18 行，最宽 70 列，手机 SSH 上不折行。每一项是什么意思按 `h`，
那一页把菜单里原本拖着的解释一次列全。

**告警只在真的出事时才占地方**，非空时插在状态格和菜单之间：

```

   [!] 检测到 netshape，它会盖掉这里的配置

```

**档位只改三个数**（整形百分比、首窗、要不要整形），不引入新机制——预设如果偷偷换掉
底层机制，面板显示的就不是实际在跑的东西了。

`8 诊断` 里的重传率是 **5 秒窗口的增量**，不是自开机累计。跑了几周的机器上，
累计值是个动不了的平均数，看不出你刚才那次改动有没有用。

命令行仍然可用（`check` / `plan` / `apply` / `status` / `revert` / `uninstall`），
非 TTY 下自动退回命令行模式，脚本化调用不受影响。

## 核心判断：分散的客户端不需要「每人一套参数」

per-route 能写的参数（`initcwnd` / `initrwnd` / `rto_min` / `advmss` / `congctl`）
几乎全是**新连接头几个 RTT** 的事。看片是长连接，这些参数对播放中途的丢包和尾峰
毫无作用。给每个地区单独配一套参数，听起来对，实际能配的东西是空的。

真正有用的是**一套按最远客户端定尺寸的配置**，加上会自己适应其余客户端的机制：

| 机制 | 解决什么 |
|---|---|
| **pacing** | 突发不会按线速灌进最慢那条末端链路 —— 混合客户端下降低重传的最大单一杠杆 |
| **BBR** | 不把随机无线丢包当拥塞信号。丢包型算法每丢一次砍一次窗，5G 上永远起不来 |
| **AQM + ECN** | 真排起队时是标记而不是尾部丢包 |
| **按设备公平** | 一台开 40 条连接的设备挤不掉只开 1 条的那台 |

**刻意不做的事：不设单流限速。** 按固定宽带调的限速会勒死固定宽带，而对移动客户端
根本不会触发 —— 它本来也没跑那么快。

## 三个目标各自靠什么

### 低重传

`fq`/CAKE 的 pacing 是第一位的。没有 pacing 时，一个 cwnd 的数据会按网卡线速打出去，
末端是 5G 或家宽时缓冲直接被冲垮。

第二位是**把瓶颈拿回本机**。VPS 出口通常被运营商限速，队列堆在他们那边——而运营商的
policer 是**丢包**式的。整形到限速的 95%，瓶颈回到本机，换成 CAKE 的**排队 + ECN 标记**。
让出 5% 峰值换真实的重传下降。

### 爬升快

- 缓冲上限按 **覆盖 RTT × 出口带宽** 的 BDP 两倍算，别让远端客户端撞到硬顶
- 默认路由 `initcwnd 20`（内核默认 10）。前面有 pacing，这一发会被摊到一个 RTT 上
- **`tcp_no_metrics_save=1`** —— 内核默认会把每个目标的 `ssthresh` 缓存下来。5G 波动时
  缓存到一个很低的值，**下一条连接会带着这个悲观值起步、提前退出慢启动**。这是波动
  链路「爬不起来」的一个直接原因，默认没人关
- `tcp_slow_start_after_idle=0`

### 稳定不掉速

- BBR 不因随机丢包塌陷
- 不设会绑死的单流限速
- `slow_start_after_idle=0`：流媒体分块之间的短暂空闲，默认行为是把 cwnd 打回初始值
  重新慢启动 —— 这是「看着看着掉速」的一个真实机制
- **按设备公平**：`fq` 是按**流**公平的。一台设备 38 条连接、另一台 1 条，`fq` 下带宽是
  38:1。CAKE 的 `dual-dsthost` 先按主机公平、再在主机内部按流公平，变成 50:50

## 为什么整形是可选但推荐的

主机公平和 AQM **只有在瓶颈队列在本机时才存在**。不整形就拿不到，只剩 pacing + BBR +
缓冲尺寸。`--no-shape` 保留这个选择，但那时脚本不会声称自己做到了公平。

## 覆盖 RTT 怎么填

**填「这台机器上最远那个客户端」的延迟。** 不是你自己到这台机器的延迟，也不是平均值。

上限只是上限：近端客户端的 autotuning 会自己停在低处，用不到那么多。但填低了，
**每个远端客户端都会撞到一个查不出原因的硬顶**。

向导和面板的 `6)` 都会**直接量一次**当前活跃客户端，给出建议：

```
  实测：当前 2 个活跃客户端里，最远的 RTT 是 277 ms
  建议填 350（实测 ×1.2 后向上取整，给移动客户端留波动余量）
```

量的时候只算**入站且真的在传数据**的连接——本机往 CDN/源站开的出站连接不是客户端，
空闲 socket 上那个 `rtt` 是陈旧值不是路径采样。

**填大不是没有代价**，向导会把这个权衡摆出来（958 MB 内存 / 500 Mbps 为例）：

```
    100 ms → 上限 11.9 MB/socket，约 27 条满上限就触发全局 tcp_mem 压力
    250 ms → 上限 29.8 MB/socket，约 11 条满上限就触发全局 tcp_mem 压力
    400 ms → 上限 47.7 MB/socket，约  6 条满上限就触发全局 tcp_mem 压力
```

所以**每台机器分别填**：同区域落地（客户端 30-60 ms）填 100 上下，跨洋中转
（客户端 150-280 ms）填 250-350。同一套配置抄到所有机器上，要么把近端机器的
内存预算白占掉，要么把远端机器的客户端封顶。

## 尺寸怎么定

覆盖 RTT 默认 **250 ms**，按**你最远的客户端**填，不是按你自己。

这条来自 [tcpfit](https://github.com/Kylin010/tcpfit)：它把 RTT 探测整个删掉改成硬编码，
理由是代价不对称 —— 估高只多付一点拥塞控制超发，**估低是每个远端客户端都撞得到、却
查不出原因的硬顶**。

缓冲上限 = BDP × 2（`tcp_adv_win_scale=1` 时内核只把一半交给应用），下限 8 MiB，
再按内存 1/16 夹住（上限是**每 socket** 的，不夹住就是小机器被自己的配置 OOM）。

## 每个键只往安全的方向动

| 方向 | 键 | 规则 |
|---|---|---|
| 只升不降 | `rmem_max` `wmem_max` `tcp_rmem` `tcp_wmem` | 上限给大几乎不亏（autotuning 会自己停在低处），调小是查不出来的硬顶 |
| 只降不升 | `tcp_notsent_lowat` | 运维已经调得更紧就保持 |
| 精确 | 其余 | 就是要这个值 |

`tcp_rmem` / `tcp_wmem` 是 `min default max` 三元组，**逐字段合并** —— 不会在同一次写入
里升一个、缩另一个。

## 安全边界

- `plan` 只读；`apply` 写之前先快照 sysctl、根队列、默认路由
- `revert` 还原到 tcpwide 介入之前，并清除持久化
- **默认路由是 ECMP、多路径、或不止一条时，一律不动** —— 错改默认路由的代价是断连
- 检测到 netshape / routetune 会中止（两者同样接管全局 sysctl 和根队列，不是叠加，
  是谁后跑谁生效）。**tcpwide 不替你卸载它** —— 卸载得由它自己的代码做，它知道自己
  改过什么（HTB 类、nginx 片段、systemd unit、自己的 sysctl 快照），tcpwide 猜不到。
  确认要覆盖才加 `--yes`
- 默认**不持久化**，重启回到原样；`--persist` 才写 `/etc/sysctl.d` 和 systemd unit

## 从 tcpfit 和 netshape 借的（v0.3.0）

**`tcp_mem`（来自 tcpfit）** —— `rmem_max` 只是天花板，`tcp_mem` 才是内核硬拦的**全局**
页预算。它太小的话，上限调多大都没用：几条大流一上来就触发压力，内核把所有 socket 的
缓冲统统缩回去。起点按 tcpfit 的公式取内存的 1/16、1/8、1/4。

**每 socket 上限夹在全局预算的 1/4** —— 留出至少 4 条大流同时到顶的余地。
不用 1/8，是因为在「小内存 + 快端口」的机器上 1/8 会把单流压得远低于端口速率，而
`tcp_mem` 本身才是防 OOM 的那道闸。

**全局预算跟着需求走，不是只跟着内存走（0.9.1）** —— 预算从 RAM/4 起步，当「4 条流各
到顶」放不下时往上长，最多长到 RAM/3。这一条是必需的：预算撞到 `tcp_mem` 高水位时内核
**是把每个 socket 的缓冲缩回去，不是 OOM**，所以在需要的时候把预算抬到内存的三分之一
是有兜底的取舍，而把预算钉死在 RAM/4 则等于用一个和端口、和路径都无关的数字，去决定
一条流最多能跑多快。

> **0.9.0 曾据此断言「520 MB 的机器只能跑到 545 Mbps」，0.9.1 撤回。** 那个数是拿
> **250 ms** 的覆盖 RTT 算的，而那台机器实测的 RTT 是 **140–176 ms**。同样的配置在
> 149 ms 上给的是 915 Mbps。需求驱动预算之后，520 MB / 1 Gbps 的机器现在是：
>
> ```
>    40 ms → 上限 11.5 MB → 窗口  5.8 MB → 1210 Mbps
>   150 ms → 上限 37.8 MB → 窗口 18.9 MB → 1055 Mbps
>   176 ms → 上限 43.3 MB → 窗口 21.7 MB → 1032 Mbps
> ```
>
> 2 核 0.5 GB 的小鸡跑得过 G 口，这是既成事实；是尺寸算法要对齐事实，不是反过来。

> **0.5.0 曾经改用 netshape 的内存档位，0.9.0 撤回了。** 档位只看内存、不看端口：一台
> 520 MB 内存但有 **1 Gbps 口**的机器，它给 16 MB → 窗口 8 MB → 149ms 上单流封顶
> 450 Mbps，**把 G 口机器当成 500M 机器配**。实测那台峰值只有 349 Mbps。
>
> 而且档位从来没有支持它的证据：当初采用它是因为 netshape 表现更好，但在那台机器上
> `raise` 拒绝下调，**档位根本没生效过**，真正起作用的是 `fq maxrate`。它要防的
> 「BBR 攒出巨大 cwnd」现在由每流限速兜住，不再需要靠压窗口。

**`+2 MiB` 固定余量（tcpfit 实测）** —— 纯 2×BDP 没有余量。tcpfit 在 300M/168ms 真机上
A/B 过：11.25 MB 平均收 257.3 Mbps，同样的缓冲 **加 2 MiB 后 272.7 Mbps**，两边都是零重传。

**`tcp_adv_win_scale=1` 和 `tcp_moderate_rcvbuf=1` 显式写死** —— 上面所有上限都是按
「应用拿到一半」算的。内核要是设成 2，应用只拿到四分之一，**那些数全部差一倍**。而关掉
autotuning 的话上限就是摆设，连接永远停在默认值涨不上去。假设必须写出来，不能默认。

**`tcp_ecn=0`（来自 netshape）** —— 我原来设 2，理由是「被动模式不主动要求，所以安全」。
netshape 明确关掉它，理由是**跨境中间盒会 blackhole ECN 协商**。那是实战结论，比我那条
理论强，而且这里恰好全是跨境路径。关掉后 CAKE 改用丢包发信号，仍然比运营商 policer 温和。

**`tcp_notsent_lowat` 默认 131072（真机夹逼对照）** —— netshape 的逻辑是 RTT ≥120ms 就设
16384，对 seek 延迟合理，对吞吐是反的：**400 Mbps 下 16 KB 只够发 0.33 ms**，代理进程
必须在这个时间内跑完一整轮「唤醒 → 读上游 → 解密 → 写下发」。

真机实测见下。它仍然是面板里的 `n)`，填 0 保持系统现值。

## 怎么在会漂移的路径上做对照

跨境路径在晚高峰的波动比你能调出来的任何差异都大。所以**单次 A 对单次 B 没有意义**，
必须用 **A → B → A 夹逼**：

```
22:26:33  16384    均 271.30  峰 421.50
22:40:05  131072   均 257.36  峰 330.02
22:41:05  16384    均 213.31  峰 288.99
```

两次 16384 之间路径自己劣化了 **-21%（均）/ -31%（峰）**。直接看原始数字，131072 的 257
夹在 271 和 213 中间，会得出"没差别"。用两次 16384 插值出 22:40 那一刻的基线再比：

```
16384（插值）   均 217.3   峰 298.1
131072（实测）  均 257.4   峰 330.0     →  +18.4%  /  +10.7%
```

**方向和机制预测的一致。** 但只有一个 B 样本、趋势只由两点估出，证据不算强 —— 要坐实
就再多跑几组 A/B/A/B/A。

更省事的办法是 `8) 状态与诊断` 里的**窗口内最高单流速率**：它在已经跑着的真实流量上
连续采样，想采多久就采多久，直到把噪声投票投掉。跑分那 9 秒受路径当时的拥塞支配。

客户端分布用 `routetune scan`——那是另一个工具的活。

## 整形的代价，说在前面

**单线程测速正是这套设计主动交换掉的那一面。** 整形按定义让出 5% 峰值，而按设备公平对
单线程跑分毫无帮助——它换来的是多设备并发时不会被一台设备挤掉。

而且 CAKE 不是免费的：它把整个出口收敛到一个 qdisc 并逐包处理。**单核 VPS 跑几百 Mbps
时，这笔 CPU 开销可能比它替掉的 policer 还贵。** `check` 和面板会在核数不够时直接警告，
单线程掉速就先用「4) 不整形」档对照一次。

## 缓冲不是越大越好——取决于线路有没有被限速

tcpfit 和 netshape 在这一点上给出相反的建议，**两边都对，只是场景不同**：

- **tcpfit 调的是干净线路**：估小是查不出来的硬顶，估大只多付一点超发。
- **netshape 调的是被限速的跨境线路**，它的注释很直白：*缓冲给太大会让 BBR 攒起巨大的
  cwnd，重传就爆了。*

跨境中转属于后者。具体到一台 958 MB 的机器、171 ms 的路径：

| 缓冲上限 | BBR 最多能塞进多少在途数据 | 相对 500M 口 |
|---|---|---|
| 30 MB（RAM/32） | 1472 Mbps | **2.9 倍** |
| 16 MB（netshape 档位） | 785 Mbps | 1.6 倍 |

BBRv1 **不会因为丢包退让**，所以那 2.9 倍的超发会被下游一直丢、它一直发。
现在两条规则取更严的那个，跨境场景下 netshape 的档位胜出。

## 每条流也要限速，不只是整形总出口

`fq maxrate` 把**每条流**限在线速。没有它，单条 BBR 流带着大窗口会探到远超链路的速率，
下游——运营商的 policer，或者你自己的整形器——把超发的部分丢掉，而 BBRv1 不认为那是拥塞
信号，于是持续制造丢包。

netshape 把它挂在整形器下面当叶子；tcpwide 之前**完全没有对应的东西**。
整形总出口不能替代给单条流限速——前者管"一共发多快"，后者管"一条能发多快"。

## 内存真的不够时它会直说 —— 但先确认「不够」是真的

小内存 + 快端口的机器上，「单流跑满端口」和「多条大流并发」可能是二选一。可能，不是必然：

```
[!] 1000 Mbps × 400 ms 本该要 97.4 MB 的上限，内存只给得起 43.3 MB。
单流因此封顶在约 454 Mbps。内存不够是物理事实，不是配置错误——
这台机器上「单流跑满 1000 Mbps」和「多条大流并发」二选一。
```

**这条警告只在真的差得远时才出现**（低于端口速率的 85%）。0.9.0 版它太爱响：拿 250 ms
的覆盖 RTT 去衡量一台实际服务 140–176 ms 客户端的机器，于是把一台跑得满 G 口的机器
判成「只能跑 545 Mbps」。**覆盖 RTT 填大一档，代价直接体现在这里** —— 填 250 ms 而实际
最远客户端只有 176 ms，就是白白多要 40% 的内存，然后被自己的余量吓住。

BDP 是物理量：一条流吃满 1 Gbps × 176ms 需要 43 MB 的 socket 缓冲，520 MB 的机器给得起。
真给不起的时候（比如 400 ms 的覆盖），工具把取舍摆出来让你选，而不是悄悄砍掉一半。

## 单流跑不满时，先判定「哪一个才是天花板」（0.10.0）

真机三个后端，同一份 0.9.0 配置（上限 32.54 MB → 可通告窗口 16.27 MB）：

| 后端 | RTT | 实测 avg | 实测 max | **这个窗口在该 RTT 上支持** |
|---|---|---|---|---|
| 岳阳 2G | 184 ms | 468.5 | 592.4 | 742 Mbps |
| 黄石 10G | 146 ms | 545.6 | 639.7 | 935 Mbps |
| 上海 2G | 135 ms | 535.6 | 629.1 | 1011 Mbps |

**三个后端全都没碰到窗口天花板**，而且离得越来越远。判据：

```
实测峰值极差   8.0%   ← 几乎不随 RTT 变
反推窗口极差  28.3%   ← 随 RTT 明显变
```

RTT 拉开 36%，速度基本不动。**窗口受限的特征是速率 ∝ 1/RTT** —— 这里没有。
速率恒定而反推窗口漂移，说明有个和 RTT 无关的东西在 600–640 Mbps 上封顶。
单条连接穿过用户态代理时基本只跑在一个核上，这是头号嫌疑。

还有一个必须点破的巧合：0.9.0 的向导印「单流封顶约 546 Mbps」，黄石实测 545.58 avg。
**这是巧合，不是印证**：那个 546 是拿 250 ms 算的，而黄石实际 146 ms，同一份缓冲在
那儿支持 935 Mbps。差一点就拿这个巧合去坐实一个错误的模型。

于是 0.10.0 把这套判定装进工具，面板 `8)` 诊断里直接给：

- **每核占用（5 秒窗口）** —— 最忙的核、平均、核数、steal 峰值。单核接近打满而平均
  不高，就直说「这个天花板和 RTT 无关，调缓冲不会让它变快」。`top` 先给的聚合数字
  恰恰是藏住这件事的那个数字。steal 单列，因为小鸡上宿主超售是完全外部的封顶。
- **缓冲余量** —— 拿**实际生效的** `rmem_max` 在这条连接自己的 RTT 上算支持速率，
  和实测比。用不到 75% 就明说「缓冲不是瓶颈，再往大调也不会变快」。
- **跨后端判据** —— 面板直接印这两行规则，好在看多个后端结果时当场套用。

## 从 tcpfit 借了一条，明确不借另一条（0.20.0）

### 方向搞反过：回程 = 服务器往国内【发】

tcpfit 的说明里写得很清楚：

> 去程只涨 1.44 倍是正常的：**去程 = 国内往服务器发**，发多快由国内那台说了算，
> 服务器只能控制接收窗口。

所以 **回程 = 服务器往国内发**，是从**客户端**视角命名的（回来的那一程）。
这正是代理下载时真正走的那条腿，也正是 0.19.0 采到的「发送方向」样本。
先前我一直按「回程 = VPS 下载」在读，方向读反了。

### 借：`tcp_[rw]mem` 的中间值 65536 → 1 MB

tcpfit 代理档用 1 MB，我们一直是 `4096 131072 …` / `4096 65536 …`。
中间值是 autotuning 的**起步值**，不是上限（封顶的是第三个值）：

```
150ms 上 64KB 起步 → 第一个 RTT 只有 3.5 Mbps，要 ~8 次翻倍才够 12 MB（≈1.2 秒）
        1MB 起步 → ~4 次翻倍（≈0.6 秒）
```

**只影响平均速度，不影响峰值**——峰值在爬完之后两边都到得了。而实测里平均一直是
峰值的 ~80%，这一截正是爬升。tcpfit 报 2.2 倍，但那个数字捆了它全部改动，
**这一个旋钮没有被单独测过**，所以留成面板 `s) → 5)` 可调。

### 不借：`netdev_budget`

tcpfit 自己的注释记着：

> budget 600(现值) 3751 Mbps　budget 300(内核默认) 3745 Mbps　差 0.16%
> ⚠ 别拿公共 10G 对端测这个——那几组变异系数 23%~45%……
> 曾经据此误判成"600 有害"，复核后推翻。

**作者自己测出来是噪声。** 抄一个原作者已经量过、量出来没差别的参数，是抄形式不抄
实质。这条明确不借，并加了断言防止以后有人又加回来。

### 也不借：整形那一套

tcpfit 的招牌功能是 iperf3 扫限速器拐点再 HTB 整形，它的收益来自「有限速器打穿突发」
的机器：

```
不限速   吞吐 481 Mbps   10 秒重传 61,266 次
限到 530 吞吐 499 Mbps   10 秒重传      5 次
```

**但这两台机器的回程重传是 0.00%。** 按 tcpfit 自己的判据就是「未发现限速器」，
它会切成纯 fq——**tcpwide 现在就是纯 fq**。它的文档也直说了这种情况：

> 瓶颈在国际链路而不是你的端口时，调服务器没用。典型表现是不限速跑也不丢包，
> 但到国内就是上不去。

## 第一个查实的外部天花板：对端的 16 MiB 接收窗口（0.19.0）

样本终于抓对了（出站、几百 Mbps），BWG 的两条：

|---|---|---|---|---|---|

| 183.232.151.102 | 16.0 MB | 173.9ms | 771.8 | 777.2 | **+0.7%** |

**吻合到 1% 以内,而且两个互不相干的对端都是 16.0 MiB**(DMIT 那边两个是 15.9)。
`16777216` 是最常见的 `rmem_max` 调优值——**自动伸缩的窗口不会齐刷刷落在 2 的整数
次幂上,配置出来的才会。**

那些测速节点的接收缓冲就是 16 MiB,在 170ms 上除出来就是 ~790 Mbps。
**这是外部上限,本机怎么调都拿不回来。**

窗口÷RTT 吻合在 5% 以内时,它就该收敛**——现在会。

## 拿发送侧的量除了接收侧的缓冲（0.19.0 修）

五个样本全是这个形状：

```
在途 16.2 MB / 实际 rcvbuf 0.1 MB = 12965%
```

**在途不可能是接收缓冲的 130 倍。** `ss` 的 `delivery_rate` 是这条 socket 的
**发送速率**——采到的是去程（VPS 往中国推流），我们在这条连接上几乎只收 ACK，
所以 `rcvbuf` 停在 `tcp_rmem[1]` = 131072。拿发送侧的在途除接收侧的缓冲，量纲就不对，
而那个四选一判定还照着 `fill < 70` 报了「autotuning 没有理由长」。

0.19.0：

- **先判方向再比同一侧的量**。`bytes_sent` / `bytes_received` 分辨收发；
  发送侧比 `sndbuf`／待发队列／对端窗口，接收侧比 `rcvbuf`／未读积压／接收丢弃。
- **收发各采一条样本**。`delivery_rate` 只有发送速率，**接收中的 socket 永远赢不了**
  按它排的名次——混合测速时两个方向都在跑，回答的是两个不同的问题。
- **比值超过 110% 直接判无效**。`12965%` 这种数字必须自己拦住，
  而不是接着往下推结论——前面几轮的错结论就是这么来的。

## 诊断根本看不到跑流量的那条连接（0.18.0）

真正的筛选条件是：

**只看入站连接。** 而跑测速时 VPS 是**主动连出去**拉流的——本地是临时端口，不在
监听表里，**整条连接对诊断完全不可见**。机器上唯一的入站连接就是 SSH，
于是它每次都被选中。

加吞吐下限只是把「拿 SSH 算出假结论」变成「测不了」——诚实了，但跑测速时照样
什么都看不到。**病根是方向过滤，我上一轮只看到了症状。**

接收缓冲这个问题跟谁发起连接无关：只要在收数据，`rcvbuf`、未读积压、接收丢弃
就都有意义。0.18.0 让 `window_ratio` 和 `peer_window_ceiling` 看两个方向，
并标注入站／出站。

`observed_client_rtt` **保持入站-only**：它给覆盖 RTT 定尺寸，问的是客户端群体分布，
出站连接本来就不该进去。

## 窗口比例诊断给出四选一（0.17.0）

`skmem` 里除了 `rb`（rcvbuf）还有 `r`（已排队未读）和 `d`（接收丢弃），
这三个数正好能分开四种病因，而它们的处方完全不同：

| 现象 | 病因 | 该动什么 |
|---|---|---|
| `r` 接近 `rb` | 应用没把数据读走 | 代理进程／CPU，**加大缓冲只会让积压更大** |
| `d` > 0 | 接收侧丢弃 | `netdev_max_backlog`、每核占用 |
| `rb` 远小于 `rmem_max` 且 `r` ≈ 0 | autotuning 没理由长 | 发送端或路径，**加大 rmem_max 没用** |
| `rb` 到顶且在途 ≈ `rb/2` | 真的窗口限制 | 这时才该加大覆盖 RTT／缓冲 |

前面两轮的错误结论，本质都是在这四种里瞎猜。

## 缓冲上限一直小了一倍（0.16.0，已撤回）

TcpQuality 的**回程速度**（VPS 自己从各节点拉流，RTT 是 VPS↔节点）第一次把这件事说死。

BWG，rmem 43.4 MB，六个重传 0.00% 的节点：

| 节点 | 速度 | RTT | 在途 |
|---|---|---|---|
| 上海电信 | 642.6 | 149ms | 11.41 MB |
| 上海联通 | 634.0 | 151ms | 11.41 MB |
| 上海移动 | 638.9 | 148ms | 11.27 MB |
| 北京电信 | 581.1 | 168ms | 11.64 MB |
| 广东电信 | 558.7 | 174ms | 11.59 MB |
| 广东移动 | 549.0 | 174ms | 11.39 MB |

**RTT 拉开 17%，在途字节只差 3%。** 教科书式的窗口封顶。

```
BWG   在途中位 11.45 / rmem 43.4 = 0.264
DMIT  在途中位  7.91 / rmem 32.0 = 0.247      1/4 = 0.250
```

**在途 ≈ rmem ÷ 4，而 tcpwide 从第一版起按 ÷2 算**（`tcp_adv_win_scale=1`，
`buffer_ceiling` 取 2×BDP）。预测对照：

| | /2 预测 | /4 预测 | 实际 |
|---|---|---|---|
| BWG @170ms | 1071 | 535 | 549–583 |
| DMIT @190ms | 706 | 353 | 375–405 |

机制还没定论——可能是 6.6+ 内核改用实测的 `scaling_ratio` 忽略了
`tcp_adv_win_scale`，也可能是接收缓冲 autotuning 根本没长到 `rmem_max`。
**两种解释指向同一个修法**，所以乘数先改成 4，同时做了 `window_ratio()`
去分辨这两者（面板 `8`）：读 `ss` 里的**实际 rcvbuf**，
`rcvbuf/rmem_max` 说 autotuning 长到了多少，`在途/rcvbuf` 说内核真给了多少窗口。

配套把每 socket 硬顶从 RAM/12 放宽到 **RAM/6**（拿并发换单流，这是明确的取舍）：

```
BWG  520MB  上限 43.3 → 86.7 MB   单流 535 Mbps → 跑满 G 口
DMIT 958MB  上限 79.8 → 159.7 MB  本来就够
```

### 0.15.0 那句结论是反的

0.15.0 的窗口报告拿 `rmem/2` 当分母，给这六个读数算出 52–54%，
结论是「缓冲不是瓶颈，**换内存更大的机器不会有任何作用**」。
按实测比例它们是 104–107%——**正顶在窗口上**。
我把一台内存受限的机器判成有余量，还劝人别换机器。那句话已删，并加断言防它再现。

### 端到端读数不能拿来判断本机窗口

同一台机器上 Impart 的单线程读数（客户端穿代理测端到端，带的是客户端的 RTT）
算出来是 **158%**。它和回程读数量的不是同一条腿。超过 115% 时报告现在会直说这一点，
而不是给一个看起来像缓冲结论的百分比。

### 顺带：手动上限低于自动值时会告警

DMIT 面板显示「缓冲上限 32 MB（手动）」——早前实验留下的固定值，按实测比例只支持
353 Mbps，而它的口子是 520，内存够到 49 MB。现在 `apply` 会说：
「手动 32.0 MB 低于自动值 49.1 MB，按 190ms 覆盖只支持约 353 Mbps，而端口是 520」。

### 持久化默认开启

`PERSIST=1`。不持久化的话每次重启机器都悄悄回到原样，下一次测速量的是没人配过的东西。
`--no-persist` 是逃生口。

## `notsent_lowat` 的争议裁决了：131072 胜 16384 四成（0.15.1）

netshape 在 RTT ≥ 120ms 时用 **16384**，tcpwide 一直用 **131072**，两边直接对立。
岳阳电信，同后端，相隔 55 秒：

| notsent_lowat | RTT | avg | max | 在途 |
|---|---|---|---|---|
| **131072** | 201ms | **458.5** | **568.4** | 13.62 MB |
| 16384 | 198ms | 282.1 | 341.2 | 8.05 MB |

**峰值低 40%，均值低 38%。**

而且这不只是一次 A/B —— **131072 那一档是可复现的**：

```
09:12  岳阳 202ms  max 580.54  (131072)
09:25  岳阳 201ms  max 568.42  (131072)   ← 13 分钟内差 2.1%
09:26  岳阳 198ms  max 341.16  (16384)    ← 比两次都低四成
```

两次 A 夹着一次 B，实质上就是 A/B/A。**netshape 那条建议在这条路径上被证伪。**

值得注意的是：`flow_limit` 是从 netshape 借来并大获全胜的，`notsent_lowat` 是拒绝
借用并被证明拒对了的。**同一个项目的两条建议，一条对一条错，只有实测能分。**

**但问题没有关闭。** 赢的只是「较大的那个」，131072 以上从没试过，方向明确是越大越好。
面板 `n)` 下一个该试 **262144 / 524288**。

## 在途字节数：分开「缓冲不够」和「别处的锅」（0.15.0）

同一台机器、同一份配置、前后几分钟：

| 后端 | RTT | 实测峰值 | 在途 = 速率×RTT | 占本机窗口 |
|---|---|---|---|---|
| 黄石 | 155ms | 927.1 | **17.13 MB** | 79% |
| 黄石 | 163ms | 881.3 | **17.12 MB** | 79% |
| 深圳 | 192ms | 583.2 | 13.35 MB | 62% |
| 岳阳 | 202ms | 580.5 | 13.98 MB | 64% |

**黄石两点的在途字节数差 0.06%。** 速率精确按 1/RTT 走 —— 同一个窗口，
差异全部来自 RTT。

而 RTT 解释不了黄石和深圳/岳阳之间的分裂：163→192ms（RTT +18%）速率掉 34%，
192→202ms（RTT +5%）速率几乎不动。**分裂是按后端分的，不是按 RTT 平滑变化的。**

最要紧的一条：**四个点全都只用到本机窗口的 62–79%，没有一个碰到上限。**
所以在这台机器上加 `rmem_max`、换内存更大的机器，**不会有任何作用**——
这正是最容易犯、也最贵的那个错误决定。

这套算术每一轮都要我手算一遍。0.15.0 把它放进工具：

```
tcpwide record 583 深圳 --rtt 192
```

面板和诊断里直接出这张表，并给出结论：占比 < 85% 就明说缓冲不是瓶颈、
换机器没用，然后按性价比列出还剩什么杠杆；≥ 85% 才说该抬缓冲。

多线程记录不进这张表——它的在途字节分摊在 N 条流上，按一个窗口去除会高估单流。

## 结果：单线程 546 → 927 Mbps（0.14.0 实测）

黄石电信 10Gb，单线程：

| 版本 | RTT | avg | max |
|---|---|---|---|
| 0.12/0.13（fq，内核队列默认） | 159ms | 429.8 | 546.4 |
| 0.14.0（`flow_limit 2048`） | 163ms | 710.9 | 881.3 |
| 0.14.0（`flow_limit 2048`） | 155ms | **756.3** | **927.1** |

**峰值 +70%，均值 +76%。927 / 1000 = 93% 线速，单线程。**

而上一轮的多线程峰值是 917.4 —— **单线程追平了多线程**。

### 因此 0.13.0 那条结论是错的，撤回

0.13.0 的面板会说：

> 聚合已经跑满端口，服务端这一侧调好了。单流低于它是每连接开销
> （代理的加解密链路 + BBR 单流行为），**改缓冲或队列都不会动它**。

**下一个版本就把它抬了 70%，动的正是队列。** 单流和聚合之间有差距，说明的是
「该往每流的方向找」，从来不是「找也没用」。0.14.1 把这句话换成指向 `s)` 里那几个
每流旋钮，并且把这次翻车写在旁边。

## 又从 netshape 借了一轮，重点是 `flow_limit`（0.14.0）

netshape-manager 能单线程跑满，所以逐项对了一遍它和 tcpwide 的差异。最值钱的一条：

```
netshape（<1GB 机器）:  fq limit 10240 flow_limit 2048
tcpwide 到 0.13.0    :  fq（内核默认 limit 10000 flow_limit 100）
```

**`flow_limit` 是「每条流」的排队配额。** 这一点决定了它的形状：

```
N 条流 → 每条各拿 100 包 → 聚合不受影响
1 条流 → 只有 100 包
```

**一个只卡单流、不卡聚合的限制**——正好是 558（单线程）对 917（多线程）的样子。

当时我写的是「机制没有被证明」，因为 fq 数的是 skb，开着 GSO 时一个 skb 能装 64KB。
**实测把它证明了：546 → 927。** 至于为什么 100 个 skb 仍然不够，还没有解释——
但结果是真机上量出来的，不是推出来的。旋钮保留着，能 A/B 回内核默认值。

其余借来的：

| 项 | netshape | tcpwide 之前 | 为什么 |
|---|---|---|---|
| `initrwnd` | 跟 initcwnd 一起设 | **主动剥掉却从不设** | 中继不只是发送方：它从上游后端拉流再转发，初始**接收**窗口决定上游那条腿爬多快 |
| `net.core.rmem_default` / `wmem_default` | 262144 | 不设 | 没显式 setsockopt 的 socket 从这里起步 |
| `net.core.optmem_max` | 4194304 | 不设 | 辅助缓冲，高并发下不够会直接分配失败 |
| `tcp_frto` | 0 | 不设 | 和 `tcp_ecn=0` 同一家族：跨境中间设备不如实转发 |
| `tcp_fastopen` | 0 | 不设 | 同上，TFO 被黑洞时握手直接卡住 |

已经有的就没重复借：`netdev_max_backlog` 早就在（连内存档位都一样），
`tcp_mtu_probing`、`tcp_ecn=0`、`tcp_no_metrics_save`、`default_qdisc=fq` 也都在。

**一个悬而未决的冲突：** netshape 在 RTT ≥ 120ms 时把 `tcp_notsent_lowat` 设成
**16384**，而 tcpwide 用 **131072**——因为我在真机上做过 A/B/A 夹逼，131072 高 18%。
两边直接对立。tcpwide 保留自己实测的那个值，但把冲突摆在面板 `s)` 里，这是下一个
该测的东西。

## 决定性的那个数：多线程 917 Mbps = 92% 线速（0.13.0）

海豚测速，华中-武汉电信 1Gb，同一后端相隔 43 秒：

| | RTT | avg | max |
|---|---|---|---|
| 单线程 | 179ms | 470 Mbps | **558 Mbps** |
| 多线程 | 175ms | 754 Mbps | **917 Mbps** |

**917 / 1000 = 92% 线速。服务端这一侧调好了。** 端口、内存、qdisc、TCP 配置全部到位，
聚合能力没有问题。单流和它之间的差距是**每连接开销**——代理的加解密链路加上 BBR 的
单流行为——**改缓冲、改队列都不会动它**。

这个数问了五轮才拿到，而它一到手，前面好几轮的猜测就全部结案了。所以 0.13.0 让工具
自己会说这句话：`record` 记下线程数，面板直接给判定。

同时 0.12.0 的回滚也被验证：不整形单线程恢复到 546–636（黄石 159ms / 岳阳 204ms /
深圳 193ms），CAKE 那次是 332，**提升 64–92%**。

## 面板上那几个假数字（0.14.1）

一次真机面板输出暴露了四处：

**1. 指纹认不出刚刚赢的那个旋钮。** `canonical_qdisc` 丢掉了 `limit`/`flow_limit`，
于是 `flow_limit 2048`（927 Mbps）和 `flow_limit 100`（546 Mbps）**指纹完全相同**。
记录日志存在的意义就是对比这种旋钮，结果它恰好分不出来。现在两者都进指纹。

**2. 根队列那行被从中间截断。** 原始 dump 有两百来个字符的内核默认值，面板 `cut -c1-58`
砍出个 `...flow_limit 2048p bucke`。改用规范化形式，信息一样但放得下。

**3. 「本机缓冲在这条 0.6 ms 上支持 303318 Mbps」。** `peer_window_ceiling` 按 delivery_rate
挑最快的连接，结果挑中一条 0.6ms 的同机房连接。算术没错，但那不是你的客户端。
现在低于 `LOCAL_RTT_SAMPLE_MS` 的连接一律不参选；全都是本地连接时直接说没有可看的。

**4. 「实时重传率 2.0000%」并跟着一句告警。** 空闲机器五秒内只发几十个报文，
一次重传就读成整整 2%——那个过于整齐的数字本身就是噪声。现在低于 2000 个报文直接
说「样本太少，不作判断」。而且那句告警原文是「先确认根队列真的是 cake」，
**在不整形档位上等于叫人去撤掉本来正确的配置**，现在按档位分支。

## 指纹必须稳定，否则 A/B 无从谈起（0.13.0）

0.12.0 的指纹直接用了 `tc` 的原始输出：

```
fq 8006: root refcnt 2 limit 10000p flow_limit 100p buckets 1024 orphan_mask 1023
quantum 3028b initial_quantum 15140b maxrate 980Mbit ...
```

`8006:` 是内核**每次 `tc qdisc replace` 重新分配**的句柄，`refcnt` 也会自己变。于是
两次完全相同的配置产生两个不同的指纹，面板那句「历史最好就是当前这份配置」
**永远不可能成立**——上一版加的功能是死代码。

`canonical_qdisc` 只保留我们自己选定的部分：

```
fq maxrate 980Mbit
cake 950Mbit dual-dsthost no-split-gso rtt 200ms
mq ← 2×fq
```

**同一份配置永远得到同一个字符串。** 这是任何 A/B 的前提。

## 单流仅剩的三个杠杆，全部只做成旋钮（0.13.0）

0.10.0 的教训：**没实测过的东西不许当默认。** 这三条都是假设，默认值一律不动，
`target_qdisc` 在旋钮为 0 时产出的 spec 和 0.12.0 逐字节相同。面板 `s)` 进去调。

- **`tcp_notsent_lowat`** —— 558 Mbps 下 128KB 只有 1.8ms 的数据量。单核机器上代理的
  调度抖动一旦超过这个数就会饿死网卡。131072 曾胜 16384（+18%），**再往上没测过**。
- **`fq initial_quantum` / `flow_limit`** —— 内核默认 15140b / 100p，后者在 558 Mbps
  下不到 3ms 的数据。高 BDP 路径上都可能偏紧。
- ~~**BBRv3**~~ —— 0.22.0 整段删掉了。换内核这件事不该由调优脚本引导，
  详见下面「BBRv3 整段删掉」。

## CAKE 在小核心机器上要掉一半速度（0.12.0）

`tc qdisc show` 摊牌的那次：

```
qdisc cake 8005: root bandwidth 980Mbit besteffort dual-dsthost ... split-gso rtt 200ms
```

同一台机器、同一个后端（上海电信），相隔几分钟：

| 档位 | 根队列 | RTT | avg | max |
|---|---|---|---|---|
| 4 不整形 | `fq maxrate 980mbit` | 135ms | 535.6 | **629.1** |
| 3 整形 98% | `cake 980Mbit` | 146ms | 284.4 | **332.3** |

**−47%。** RTT 只差 8%，而且已确认不受窗口限制，解释不了 47%。这是这批数据里最干净
的一次对照：**CAKE 在这台单核机器上吃掉一半吞吐。**

机制是 CAKE 的每包成本，尤其 `split-gso`：它把 64KB 的 GSO 超级包拆成 ~44 个 MTU 包
才能精确 pacing，每包工作量翻几十倍，再叠 `dual-dsthost` 的逐包哈希。

### 三个要认的设计错误

1. **向导默认档位是 2（CAKE 95%）。** 在一台 CAKE 会腰斩吞吐的机器上，默认值把人
   推向 CAKE。现在默认值**由机器决定**：`核数 × 300 < 出口带宽` 就默认 4，并说明理由。
2. **档位 3 叫「速度优先」，而它是这台机器上最慢的选项。** 标签描述的是整形松紧，
   却被写成速度承诺。全部改名为「整形 90%/95%/98%/不整形」——名字只说它做什么，
   速度由实测说。配置键名不动，老配置照常加载。
3. **`SHAPE_MBPS_PER_CORE` 我从 400 抬到了 600，正好删掉了会拦住这次的警告。**
   `2 核 × 400 = 800 < 1000` 会警告，`× 600 = 1200` 不会。抬它的理由是「2c0.5g 能跑
   2G」——那是**端口**能力，不是 **CAKE 每包处理**能力。拿前者调后者的阈值是把两件
   事混为一谈。现在是 **300**，锚在实测上：请求 980Mbit CAKE，实际交付 332。
   （那台机器实际是**单核**，我先前读成 2 核也是错的。）

另外**档位 3 本身两头不讨好**：整形的意义是待在下游 policer 之下，整到线速 98% 等于
没整，却付了 CAKE 的全额 CPU 成本。

### CPU 紧张时自动加 `no-split-gso`

这是唯一能让小机器**既要按设备公平又要速度**的旋钮：不拆 GSO 超级包，每包成本掉一个
数量级，代价是 pacing 粒度变粗。老内核不认这个关键字时**只丢这一个选项**，退回不带它
的 CAKE，而不是一路退到 `fq`——`ecn` 那次就是反应过度丢掉了整个 AQM。

## 测量记录：让八轮盲配变成一张表（0.12.0）

到 0.11.0 为止已经八轮「装好、随便选一档、测速、还是慢」，而谁都说不清哪个数对应
哪份配置。0.11.0 的指纹解决了「这是什么配置」，0.12.0 解决「哪份配置更快」：

```bash
tcpwide record 629.1 "上海 不整形"
```

写进 `/var/lib/tcpwide/measurements`，和 `config_fingerprint` 绑在一起。面板顶部显示
历史最好成绩；不是当前这份配置时会把那份配置一起印出来。面板 `m)` 直接录入。

没有它，每一轮都从观点开始。

## 0.10.0 把 `mq` 挂叶子设成了默认，三个后端齐掉 44% —— 0.11.0 撤回

| 后端 | 0.9.x RTT/峰值 | 0.10.0 RTT/峰值 | 变化 |
|---|---|---|---|
| 黄石 | 146ms / 639.7 | 158ms / 357.5 | **−44.1%** |
| 上海 | 135ms / 629.1 | 138ms / 335.7 | **−46.6%** |
| 岳阳 | 184ms / 592.4 | 177ms / 341.0 | **−42.4%** |

三条互相独立的路径不会同步掉 44%，所以是服务端侧的共因。归因也很干净：
`git diff 0.9.1 0.10.0` 里唯一改变内核行为的只有 `apply_fq_leaves`，其余全是文案和
诊断，`buffer_ceiling` 一字未动。

**这套布局是纯推理出来的，一次没测就设成了默认。** 根 fq 才是有实测支撑的那个
（黄石 220→349 那次就是它）。规矩本来就写在这份文档里，是我自己没守：默认值跟着实测走。

而且它本身就比根 fq 脆弱：

- **根 fq** —— 一次写入，一种失败模式，全部流量必然被 pacing。
- **mq 挂叶子** —— N 次独立写入。任何一个叶子没写上就退回内核默认
  （`fq_codel`/`pfifo_fast`），**那条队列上完全没有 pacing**。BBR 在没有 pacing 的
  队列上按 cwnd 成串突发，跨境 policer 直接丢，而 BBRv1 不把丢包当拥塞信号。

而 0.10.0 的代码写的是 `(( ok > 0 )) || return 1` —— **部分成功也算成功，照样打印
「已设为」**。半套 pacing 比没有 pacing 更糟：它是间歇性的，看起来像网络问题。

0.11.0 的处置：

1. **默认改回根 fq**。`QDISC_LAYOUT=root` 是默认，`mq-leaves` 降级为显式开关
   （面板 `l)`），代码和测试都留着——它是个待测的假设，不是废弃品。
2. **全有或全无**。任何叶子写失败就回滚已写的，退回根 fq。
3. **`mq_leaves_with` 要求每条发送队列都挂上**。之前只要 `n > 0`，于是 4 个叶子只挂了
   1 个也报「一致」，正好把 2 里那个部分状态藏了起来。

## 应用后回读，不拿 `tc` 的退出码当结论（0.11.0）

`tc` 返回 0 只说明命令被接受，不说明接口变成了想要的样子。0.11.0 应用完重新
`tc qdisc show`，把**实际生效的**布局打出来，不一致就报警：

```
[OK] 根队列保持 mq，2 个发送队列各挂一份：fq maxrate 950mbit
  实际生效：mq root ← 1×fq 1×fq_codel
[WARN] mq 的叶子没有全部挂上 fq —— 没挂上的那些队列完全没有 pacing
```

这和 0.7.x「面板把目标值当成生效值打印」是同一类 bug，那次已经付过一次学费：
整整一轮分析建立在一个从未生效的数字上。

## 配置指纹：让每张测速截图能对上一份配置（0.11.0）

`status`、面板顶部、`apply` 结尾各打一行：

```
tcpwide 0.11.0 ｜ bbr ｜ rmem 43.3 MB ｜ fq maxrate 950mbit ｜ initcwnd 20 ｜ cover 176 ms
```

全部取**实际生效值**。这一整轮之所以要靠 `git diff` 两个发布版本才知道测的是什么，
就是因为截图里没有任何配置信息。测速截图旁边贴一行指纹，归因就是查表而不是争论。

顺带把 `net.core.default_qdisc=fq` 加进 sysctl 集合：它只影响**新建**的 qdisc，
是给「内核自己建的队列也带 pacing」兜底，BBR 配 fq 是标准搭配。

## 根队列保持 `mq`，不整形时把 pacer 挂到每条发送队列上（0.10.0，已降级为开关）

`mq` 是驱动给多队列网卡放的根：**每个硬件发送队列一个子 qdisc，各自一把锁**，
核与核之间发包不用互相串行。`tc qdisc replace root fq` 会把它整个换掉，于是所有
发送队列挤进一个 qdisc 一把锁——单线程测速上完全看不出来，但对「小核心数机器冲聚合
带宽」正好是反着的。

所以不整形时保留 `mq`，往每个叶子挂一份 `fq maxrate`。整形是唯一还得占根的情况：
CAKE 只能整形它看得见的全部流量，那点串行是换 AQM 的代价。

面板的漂移检测也跟着改：`mq` 根 + 叶子挂着 pacer 是**预期布局，不是漂移**，
否则面板会催你对一个本来就正确的配置反复按「重新应用」。

## 接收窗口就是单流上限：窗口 = 缓冲 ÷ 2

`tcp_adv_win_scale=1` 时内核只把接收缓冲的**一半**当窗口用，而
**单流速率 = 窗口 ÷ RTT**。所以缓冲上限直接决定单流天花板：

| 缓冲上限 | 可通告窗口 | @160ms | @225ms |
|---|---|---|---|
| 16 MB（netshape 档位） | 8 MB | 419 Mbps | 298 Mbps |
| 32 MB | 16 MB | 839 Mbps | 597 Mbps |
| 43.3 MB（0.9.1 在 520 MB 机器上给的） | 21.7 MB | 1136 Mbps | 807 Mbps |

真机三个后端的实测反推窗口都落在 7–10 MB，**速率差得很大但窗口几乎不变**——这正是
「窗口受限」的特征（速率 = 窗口 ÷ RTT，RTT 越大速率越低）。160ms 那个后端预测 419、
实测峰值 421。

面板 `b)` 可以手动指定缓冲上限，**它会跳过内存档位**——档位正是要测的东西，不能反过来
夹住测试。

**往大调之前先确认 `fq maxrate` 生效。** 内存档位当初存在的理由是防 BBR 攒出巨大 cwnd，
而每流限速一旦到位，超发就由 pacing 速率兜住而不是靠窗口兜住，档位可能在白白牺牲窗口。
两者缺一不可：只放大缓冲不加 pacing，就回到重传爆掉的老路。

## 单流跑不到线速时，先看这一条

**单流永远不会超过「对端愿意收多少 ÷ 往返时间」。** 这台机器改不了对端那个数。

`8) 状态与诊断` 会把它直接算出来：

```
最快的那条连接：203.0.113.9
  RTT 171.0 ms｜对端通告窗口 8.7 MB｜实测 427.8 Mbps
  对端窗口决定的单流上限：427.8 Mbps
```

**但要小心把它当成结论。** 对端的窗口是**自动伸缩**的：我们推得多快，它就长到多大。
所以「窗口恰好等于实测速率」既可能是"对端封顶了"，也可能只是"对端跟着我们的发送量长到
那里就够了"——两个方向都解释得通。

真机上就是这样：netshape 在**同样的对端**上跑满过 500 Mbps，证明那个对端能给出更大的窗口。
所以这一栏是**一条要排除的可能**，不是一个诊断结论。真正判定要靠：多线程能到线速、
单线程到不了，那才是对端窗口的锅。

## 换个后端就差 63%，那是路由不是配置

同一台机器、同一套配置、相隔 71 秒：

```
23:14:44  湖北黄石[10Gbps 后端]  RTT 157  均 220.02  峰 299.09
23:15:55  湖南岳阳[2Gbps 后端]   RTT 171  均 358.72  峰 427.79
```

后端带宽更大的那个反而更慢。服务端配置对两者完全一样，所以差的 63% 是**路径**。
调优改变不了你和某个地区之间的路由质量。

## 做不到的事

无线层丢包服务端消不掉。主线内核只有 BBRv1，想要更新的 BBR 就得换内核——
那是一次重启和一台正在跑流量的机器，脚本不碰。`check` 会告诉你当前内核
实际能提供什么，`pick_cc` 就在这个范围里选最好的那个。
