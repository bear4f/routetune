# tcpwide 调参规范（1.0.0 基线）

这份文件是**结论**，不是编年史。每一项写清楚：值是多少、怎么推出来的、
证据是什么、以及为什么不是别的值。

过程记录在 [DECISIONS.md](./DECISIONS.md) —— 二十轮里撤回过什么、
哪些结论是错的、错在哪。**改这里的任何一个值之前先读那份。**

> 这些值由 `self-test.sh` 的「1.0.0 调参基线：锁死」一节逐项断言。
> 改动默认值会让自测变红——这是有意的。README 会被跳过，红的测试不会。

---

## 一、总原则

**按最远的客户端定尺寸，不按你自己。** 分散在多个地区的客户端不需要
「每人一套参数」，需要的是一套按最远那个定尺寸、其余靠内核自适应机制兜住的配置。

**每个键只往安全的方向动。** 缓冲上限给大几乎不亏（autotuning 会让近端连接
自己停在低处），给小才是每个远端客户端都撞得到、却查不出原因的硬顶。
所以上限类的键标 `raise`（只升不降），行为类的键标 `exact`。

**起步值是例外，必须能双向走。** `tcp_[rw]mem` 中间那个字段是 autotuning 的
**起点**，不是上限——它的全部代价是每 socket 都要付。把整条元组标成 `raise`
曾经造出一个只升不降的棘轮：写过一次 1 MiB 的机器再也退不回来。
所以它是 `raise,exact,raise`。

**没实测过的值不许当默认值。** 这条规矩破过一次：一个从 tcpfit 抄来的常数
在用户机器上活了四个版本。

## 二、拥塞控制与队列

### `net.ipv4.tcp_congestion_control = bbr` · exact
无线末端链路上的随机丢包不是拥塞。丢包型算法（cubic/reno）每丢一次砍一次窗，
4G/5G 客户端永远起不来。内核给什么就用什么（`bbr3 > bbr2 > bbr`），
这是**在已有的里面选**，不是换内核。

**不做 BBRv3。** 主线只有 v1，要 v3 就得换内核——在一台正在跑流量的机器上
换内核不是调优脚本该引导的事，520 MB 的机器 `/boot` 也未必装得下第二个内核。

### `net.core.default_qdisc = fq` · exact
BBR 必须配 pacing。内核自己新建的队列（mq 叶子、新网卡、队列数变化）走这个
默认值，而装机默认值不做 pacing——一个没有 pacing 的队列会按线速发 cwnd 大小的
突发，正好喂给下游的 policer 丢掉。

### 根队列
| 档位 | 队列 |
|---|---|
| 整形 90/95/98% | `cake bandwidth <口速×档位%> dual-dsthost besteffort rtt <覆盖RTT> [no-split-gso]` |
| 不整形 | `fq limit <L> flow_limit <F>` |

**不整形档不写 `maxrate`。** `maxrate` 是 **per-flow** 上限。0.22.0 及以前它
无条件从端口速率推出来，于是「我的口是 2 Gbps」被翻译成「任何一条连接不得超过
1.9 Gbps」，而且不整形档也照写——那一档的全部意义就是不限速。
单流上限现在默认 0，只有操作员显式设置才写。

`no-split-gso` 只在核数撑不住端口时加：`split-gso` 是 CAKE 的主要每包成本，
它把一个 64KB 的 GSO 超包拆成约 44 个 MTU 包。实测同机同后端，
fq 峰值 629 Mbps，CAKE 只有 332。

`limit` / `flow_limit` 按内存分档（借自 netshape）：<1 GB 用 `10240 / 2048`，
≥1 GB 用 `40960 / 8192`。内核默认 `flow_limit` 是 100 包，在 558 Mbps 下
不到 3ms 的数据。

## 三、缓冲

### `net.core.rmem_max` / `net.core.wmem_max` · raise
```
上限 = 2 × BDP + 2 MiB      BDP = 端口速率(Mbps) × 125 × 覆盖RTT(ms)
再按 RAM/12 夹住
```

**为什么是 2 倍**：`tcp_adv_win_scale=1` 时内核只把接收缓冲的一半交给应用当窗口用。
**为什么加固定的 2 MiB**：tcpfit 在 300Mbps/168ms 上 A/B 过——11.25MB 平均 257.3 Mbps，
同样的缓冲加 2MiB 平均 272.7，两者都是零重传。固定余量能拿回这部分，
又不会把大机器按比例放大。

**为什么不是 4 倍**：0.16.0 从两台机器推出「在途 ≈ rmem_max/4」，把乘数改成 4。
下一组数据把 rmem_max 从 43.4 MB 翻倍到 86.8 MB，**在途从 11.41 MB 变成 11.40 MB**。
两台机器的相关性不是因果。已撤回。

### `net.ipv4.tcp_rmem` / `net.ipv4.tcp_wmem` = `4096 <起步> <上限>` · raise,exact,raise

**中间字段是起步值，不是上限。** 它决定爬升快慢，不是吞吐天花板，也不是 cwnd。

| 档位 | 起步值 |
|---|---|
| 整形 90% / 95% | `0`（保持内核自己的值） |
| 整形 98% / 不整形 | `1 MiB` |

1 MiB 是暖启动：160ms 路径上 64KB 起步的第一个 RTT 只有 3.5 Mbps，
要八次翻倍才够用；1 MiB 起步只要四次。代价是**每 socket 都吃这么多额度**，
所以只给两个明确追吞吐的档位，不是所有档位都付。

方向必须是 `raise,exact,raise`：第三个字段（上限）继续只升不降，
中间字段必须能降回去——否则就是棘轮。

### `net.core.rmem_default` / `net.core.wmem_default` = 262144 · raise
没显式 `setsockopt` 的 socket 和所有非 TCP socket 从这里起步。TCP 自己走
`tcp_[rw]mem`，所以这两个只兜底。

### `net.ipv4.tcp_mem` · raise
全局 TCP 页预算，**所有 socket 共享**。`rmem_max` 只是每 socket 的天花板，
这个才是内核硬拦的总量：它太小的话，上限调多大都没用，几条大流一上来就
触发压力被缩回去。

### `net.core.optmem_max = 4194304` · raise
辅助缓冲上限。高并发下不够会直接分配失败。

## 四、爬升

### 默认路由 `initcwnd` / `initrwnd`

| 档位 | 首窗 |
|---|---|
| 整形 90% | 16 |
| 整形 95% | 20 |
| 整形 98% / 不整形 | **64** |

**证据**：0.29.0 把高速档的首窗从 64 降到 32，随后四个地区**全部**回退到
约 35–113 Mbps。0.29.1 恢复 64。这是这套配置里少数有直接实测支撑的值之一。

`initrwnd` 和 `initcwnd` 一起设：中继不只是发送方，它还要从上游拉数据再转发，
**初始接收窗口决定上游那条腿爬多快**。只设 `initcwnd` 会让每条连接有一半
从内核默认值起步。

### `net.ipv4.tcp_slow_start_after_idle = 0` · exact
内核默认会在连接短暂空闲后把 cwnd 打回初始值重新慢启动，
而流媒体分块之间正好是这种空闲——这是「看着看着掉速」的一个真实机制。

### `net.ipv4.tcp_pacing_ss_ratio` —— **默认不写**
慢启动期的 pacing 倍率，内核默认 200（按估计速率的两倍发）。
`initcwnd` 只决定第一个 RTT 发多少，这个决定**后面每一个 RTT 爬多快**。

面板 `s → 6` 里是个旋钮，但**默认不动**：它在这里从没实测过。

## 五、跨境路径上的取舍

### `net.ipv4.tcp_ecn = 0` · exact
跨境中间盒会 blackhole ECN 协商（netshape 的实战结论）。关掉后 CAKE 改用
丢包发信号，仍然比运营商那个 policer 温和得多。

### `net.ipv4.tcp_fastopen = 0` · exact
TFO 是**协商型**扩展，中间盒处理不了 cookie 会直接卡住握手。

### `net.ipv4.tcp_mtu_probing = 1` · exact
路径上有人钳制 MSS 时让内核探到能用的大小，而不是反复重传大包。

### `net.ipv4.tcp_adv_win_scale = 1` · exact
决定接收缓冲里划给窗口的比例，上面所有上限都是按「一半」算的。

**注意**：6.6 起内核内部改用实测的 `tcp_scaling_ratio`，这个键不再是跨内核的
硬保证。所以工具**不再断言**「窗口 = 缓冲 ÷ 2」，而是从 `ss` 量出真实比例。

### `net.ipv4.tcp_moderate_rcvbuf = 1` · exact
接收缓冲自动伸缩。关掉的话上限就是摆设——连接永远停在默认值。

### `net.core.netdev_max_backlog` · raise
网卡收包队列，按内存分档。太小会在进入协议栈之前就丢包，看起来像上游丢包。

## 六、明确不做的

| 项 | 为什么不做 |
|---|---|
| **BBRv3 / 换内核** | 要重启一台正在跑流量的机器。调优脚本不该引导这件事 |
| **`tcp_notsent_lowat`** | 曾默认 131072，实测「胜 16384 四成」——但那次是**带着 `fq maxrate` 测的**。cap 拿掉后 regime 已变，证据作废。回归系统默认 |
| **`tcp_frto = 0`** | 借自 netshape，理由写的是「依赖中间设备如实转发」——**错的**。F-RTO(RFC5682) 是纯发送端算法，靠 ACK 流判断伪超时。已撤回 |
| **`tcp_no_metrics_save = 1`** | 要防的是 ssthresh 被缓存成低值，但 `tcp_no_ssthresh_metrics_save` **自 5.6 起默认就是 1**。强制前者等于丢掉整个目标缓存（RTT/RTTVAR/cwnd/reordering）去修一个内核已经修好的问题。已撤回 |
| **`netdev_budget`** | tcpfit 自己的注释记录 600 vs 300 = 3751 vs 3745 Mbps，**0.16%，是噪声** |
| **`tcp_limit_output_bytes`** | 默认 4 MiB，在 2 Gbps 下是 16ms 的数据。算过了，不是瓶颈 |
| **policer 拐点扫描 / HTB 整形** | tcpfit 自己的判据在零重传的机器上就是「没找到 policer」 |
| **单流限速** | 见上面「不整形档不写 maxrate」 |

## 七、这套配置改变不了的

- **不同地区之间的差距**。同一台机器、同一分钟、RTT 141–169ms 几乎一样的四个后端，
  平均速度 122 / 215 / 494 / 790 Mbps。那是回程路由和后端，服务端 sysctl 碰不到
- **对端的接收窗口**。实测抓到过在途 = `snd_wnd` 的 100%：22.5 MB ÷ 131.8ms
  = 1432 Mbps，而实测峰值 1400。那是客户端的 `rmem`
- **无线末端的丢包**。BBR 不把它当拥塞信号，但消不掉它
- **单核 CPU 上限**。用户态代理和加密基本只用得到一个核
